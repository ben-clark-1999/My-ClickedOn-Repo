8. Bug 1 — silent hand-off failure

Discovered that the error was in /src/lib/pipeline.ts in the generate() function, 3 separate
issues:
- No await keyword used — advanceToNextStage() is async, so calling it returns a promise. Without
  the 'await' keyword, the function does not pause to find out the outcome.
- .catch(() => {}) swallows the failure — usually, if a promise is rejected, Node raises an
  'unhandled rejection' warning, so the user would see something in logs. This empty catch handler
  gets the rejection and does nothing with it. The failure is now invisible, no logs.
- return { status: "ok" } runs immediately — since nothing waited, this line executes before the
  handoff succeeds or fails. 'ok' is returned by default.

How I verified the bug was fixed:
- Immediately after the fix, I ran npx vitest run -t "failed hand-off" which passed.


9. Bug 2 — truncated stream crashes the run

Discovered that the error was in /src/lib/pipeline.ts lines 31-34, where the code asks the model
for a draft exactly once and assumes it worked. There are 2 main issues here:
- The model's reply can get cut off halfway through the response, so the closing ``` never
  arrives. extractJson can only work if the opening and closing markers are both there, so on a
  cut-off reply it throws 'No fenced JSON block found'.
- Nothing catches that error. There is no try/catch around these lines, so the error travels all
  the way up and crashes the entire run. One brief connection drop crashes the whole request, when
  it should just ask the model to try again.

Fix:
- Wrap the model call in a retry loop (maximum of 3 attempts). If all 3 attempts fail, return
  "error" instead of looping forever.
- The retry works because the same state object is passed in each time. If a fresh state were
  passed in each attempt, the counter would reset and the mock would never move past the failure.

How I verified the bug was fixed:
- npx vitest run -t "truncated stream" passed immediately after the fix. The full npm test jumped
  1 -> 3 of 4 (this one change fixed Bug 2 AND Bug 3a). typecheck / lint / build all stayed green.


10. Bug 3a — transient 429s kill the run

This was already fixed by the Bug 2 retry loop. A 429 error happens when you call a real API too
many times too quickly. This error is caught in the same try/catch block as the truncated output
from the LLM.

How I verified the bug was fixed:
- npx vitest run -t "rate-limit" -> passed. No separate code change — the Bug 2 retry loop
  covered it.


11. Bug 3b — unbounded revision loop

This bug occurs at pipeline.ts:52-56. There are two main problems with it:
- 50 is the wrong number — the repo already defines the official limit MAX_REVISIONS = 3. The
  loop just ignores it and makes up the value of 50.
- The loop can end for two different reasons: review finally passed (success), 
  or we ran out of attempts (failure). The code never checks which one happened.
  Regardless of what happens, execution falls straight through to the hand-off and
  return { status: "ok" }. This is the same problem as the first bug, a failure disguised as
  an ok.

How I verified the bug was fixed:
- npx vitest run -t "never passes" now passes.
- npm test -> 4/4, typecheck / lint / build all green.

13. Bonus test

The README says: "add one test of your own that covers an edge case you think matters. We notice
this."

Instead of letting the AI write whatever test it wanted, I opened a new context window with model
set to Fable 5 and thinking set to X-high, asked it to scan the project README.md, gave it the
instruction "Bonus: add one test of your own that covers an edge case you think matters. We
notice this", directed it to src/__tests__/pipeline.test.ts, then asked it what the most
important missing edge case was.

The answer: all 4 existing tests only check what generate() RETURNS (status and attempts). None
of them check what it actually DOES — specifically, whether advanceToNextStage gets called or
not. That means a bug where a failed draft still gets handed off to the next stage would slip
straight past every test. In the real pipeline that would mean unreviewed content getting
shipped, which is much worse than just a wrong status code.

My test (in a new file, src/__tests__/handoff-side-effects.test.ts, since the original test file
is protected):
- If review never passes, advanceToNextStage must be called 0 times.
- If the run succeeds, it must be called exactly once (not zero times, not twice).

How I verified the test itself actually works:
- I temporarily swapped the original broken pipeline.ts back in and ran my new test -> it FAILED.
  That proves the test genuinely catches the bug (a test that can never fail proves nothing).
  Then I restored my fixed version with git checkout.
- npm test -> 6/6, typecheck / lint / build all green.
- Double-checked the two protected files are still byte-identical to the originals.
